# 스킬 템플릿

반복 업무를 스킬로 만들 때 쓴다. 생성한 스킬의 독자는 인터뷰를 보지 못한 에이전트이고, 그 에이전트는 매 실행마다 이 파일만 보고 일한다. 스펙 작성 규칙(줄임말 금지, 하지 않을 것 명시, 결정에 이유 붙이기)이 그대로 적용된다.

폴더 구조:

```
<이름>/
├─ SKILL.md            # 실행 절차. 500줄을 넘기지 않는다
└─ references/         # 필요할 때만
   ├─ examples.md      # 사용자가 좋다고 한 결과물 예시
   └─ <긴 기준표>.md    # 체크리스트, 스타일 가이드 등 길어서 본문에 두기 어려운 것
```

`references/` 파일은 SKILL.md에서 "어느 단계에서 읽는지"를 적어 둔 것만 만든다. 아무도 읽으라고 하지 않는 파일은 읽히지 않는다.

## SKILL.md 틀

`<...>`를 채운다. 해당 없는 절은 "해당 없음"과 이유를 한 줄로 적는다. 단, "주의할 점", "프로세스 수정", "변경 이력"은 비어 있어도 지우지 않는다. 사용자가 고친 방식과 실행 중 알게 된 것이 쌓이는 자리다.

```markdown
---
name: <이름>
description: <무엇을 하는 스킬인지 한 문장>. <언제 쓰는지>. 트리거 — "<사용자가 실제로 쓸 문구>", "<문구>", "/<이름>".
---

# <제목>

<이 업무가 무엇이고 결과물이 누구에게 어떻게 쓰이는지 두세 문장. 목적을 알아야 절차에 없는 상황에서도 같은 방향으로 판단한다.>

## 입력

| 입력 | 필수 | 없을 때 |
|---|---|---|
| <주제, 파일, 링크 등> | 예 / 아니오 | <물어본다 / 기본값 X를 쓴다> |

필수 입력이 빠졌으면 한 번에 모아서 묻고, 나머지는 기본값으로 진행한다.

## 고정 규칙

매 실행마다 지킨다. 바꾸려면 아래 "프로세스 수정"을 따른다.

- <톤, 형식, 분량, 금지 사항 등> — <이유>

## 절차

### 1. <단계 이름>

<무엇을 하는지>
- 산출물: <이 단계가 끝나면 있어야 하는 것>
- 넘어가는 조건: <확인할 것>

### 2. <단계 이름> 🔸 사용자 확인

<사용자에게 무엇을 보여주고 무엇을 승인받는지. 승인 전에는 다음 단계로 가지 않는다.>

...

## 주의할 점

실행하다 걸려 넘어졌던 곳. 해당 단계를 시작하기 전에 읽는다.

- <처음엔 비어 있어도 된다. "프로세스 수정"으로 채워진다>

## 품질 기준

결과물을 넘기기 전에 하나씩 확인한다.

- [ ] <관찰 가능한 기준>

<examples.md가 있으면: "형식과 톤은 `references/examples.md`의 예시에 맞춘다. 예시를 베끼지 말고 수준을 맞춘다.">

## 출력

- 형식: <파일 형식, 구조>
- 저장 위치: <경로와 이름 규칙. 예: `content/YYYY-MM-DD-<슬러그>.md`>
- 끝나면 알릴 것: <경로, 사용자가 채워야 할 곳, 다음에 할 일>

## 프로세스 수정

이 스킬은 쓸수록 나아지게 만들어졌다. 이 업무에 관한 사용자의 선호와 수정, 실행 중 알게 된 것은 메모리나 대화가 아니라 이 스킬 파일에 남긴다. 그래야 이 업무를 할 때만 읽히고 다음 실행에 그대로 이어진다.

**사용자가 고칠 때.** 실행 중 사용자가 결과물이나 절차를 고치면:

1. 이번만인지 앞으로도인지 가린다. "다음부터", "앞으로", "항상", "이 단계는 빼", "이건 매번 이렇게" 같은 말이면 앞으로도다. 이번 입력에만 해당하는 수정(이 주제라서, 이번 마감이라서)은 이번만이다. 애매하면 "앞으로도 이렇게 할까요, 이번만 할까요?"라고 한 줄로 묻는다. 같은 종류의 수정이 두 번째 나오면 앞으로도 적용할지 먼저 묻는다.
2. 앞으로도면 바로 고치고, 이번 실행의 남은 부분에도 적용한다.

**스스로 발견했을 때.** 절차에 빠진 단계, 틀린 명령이나 경로, 겪어 보고 알게 된 함정이 있으면 실행을 끝내기 전에 고친다. 사실을 바로잡거나 함정을 적는 것은 고치고 알리면 된다. 결과물이 달라지는 변경(단계 추가·삭제, 고정 규칙 변경)은 사용자에게 먼저 묻는다.

**고치는 방법.**

- 해당 단계, 고정 규칙, 주의할 점의 문장을 직접 고친다. 맨 아래에 덧붙이지 않는다. 옛 규칙과 새 규칙이 둘 다 남으면 다음 실행이 어느 쪽을 따를지 모른다. 파일 전체를 다시 쓰지 말고 바뀌는 부분만 고친다.
- 기록이 아니라 교훈으로 쓴다. "2026-11-03에 제목이 길어서 지적받음"이 아니라 "제목은 30자 이내로 쓴다. 목록 화면에서 잘린다"처럼 지시와 이유를 한 줄에 쓰고, 한 줄에 규칙 하나만 둔다. 날짜와 경위는 변경 이력에만 적는다.
- 새 단계는 순서에 맞는 자리에 넣고 번호를 다시 매긴다. 길어진 기준표는 주제 이름의 `references/` 파일로 옮기되, 비슷한 파일이 있으면 새로 만들지 말고 거기에 더한다. SKILL.md는 500줄을 넘기지 않는다.
- 사용자가 좋다고 한 결과물은 `references/examples.md`에 넣을지 묻는다. 예시는 최대 5개, 넘으면 가장 오래된 것을 뺄지 묻는다.

**고친 뒤.** 변경 이력에 날짜, 무엇을 바꿨는지, 왜 바꿨는지를 한 줄로 남기고, 사용자에게 "SKILL.md의 <절>을 <전> → <후>로 고쳤습니다"라고 알린다. 되돌리라고 하면 되돌리고 그것도 이력에 남긴다.

목적(맨 위 설명)과 이 "프로세스 수정" 절은 사용자가 명시적으로 바꾸라고 할 때만 고친다.
```
